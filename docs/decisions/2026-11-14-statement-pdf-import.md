# 거래내역서 PDF를 서버에서 읽어 검토 없이 모두 저장

- 날짜: 2026-11-14 · 결정한 사람: 사용자 · 관련: Issue #327
- 영향: 앱 화면 / 앱 서버 / 개인정보처리방침

## 결정

- PDF는 서버에서 읽는다(11-09 결정). 첫 지원 형식은 신한은행 "거래내역조회" PDF이고, 다른 은행·카드사는 샘플을 받으면 형식별로 더한다.
- **검토 화면을 두지 않고 읽은 거래를 모두 저장한다.** 6개월치를 사용자가 하나씩 확인하지 않고, 확인이 필요한 것만 골라 보여 줘도 판별이 어렵고 사용자도 기억하기 어렵기 때문이다.
- 토스페이·카카오페이 등 간편결제 출금은 결제(지출)로 본다. 본인 계좌 사이 이체도 따로 거르지 않는다.
- 카테고리는 스크린샷 가져오기와 같은 이름 규칙으로 추정한다. 카테고리 세분화는 별도 업데이트에서 다룬다.
- 파일을 고르면 바로 비밀번호 모달을 띄우고 숫자 키패드로 입력받는다. 비밀번호는 PDF를 여는 데만 쓰고 저장하지 않는다.
- 저장은 온보딩 마지막 단계(예산 설정 저장)를 기다리지 않고 올린 즉시 한다. 같은 PDF를 다시 올려도 같은 거래(종류·금액·시각·제목)는 건너뛰고, 잔액 기준 시각 이후 거래는 넣지 않는다.
- 읽은 줄이 하나라도 이상하거나 잔액이 이어지지 않으면 전체를 거절한다(일부 저장 없음).

- (2026-11-14 추가) KB국민은행 "계좌 거래내역 조회" PDF도 받는다. 사용자 6개월치 실제 파일로 확인(791건, 전 구간 잔액 연결). 응답 `bank`에 `KB`를 더했다(계약 변경, 옛 앱은 이 값을 쓰지 않음). 검토 없이 모두 저장하는 규칙은 같다.

## 구현·호환성

`POST /transactions/statement-import`(multipart: `file`, `password`)와 오류 코드 `STATEMENT_PASSWORD`·`STATEMENT_UNSUPPORTED`를 `app-api.yaml`에 더했다. 기존 응답은 바뀌지 않는다. 서버는 PDFBox로 글자를 뽑아 파싱하고(`statement` 패키지), 업로드 한도를 10MB로 올렸다. 앱은 `expo-document-picker`를 더해 **새 빌드가 필요**하다. 서버를 먼저 배포한다. 규칙과 예시는 [policies §9](../policies.md).

실제 거래내역서는 저장소에 넣지 않는다. 테스트는 가짜 값으로 만든 글자 줄·PDF를 쓰고, 실제 파일 확인은 `STATEMENT_SAMPLE_PDF`·`STATEMENT_SAMPLE_PASSWORD` 환경 변수를 줄 때만 도는 로컬 테스트(`StatementPdfReaderTest`, 건수만 출력)로 한다.
