## 한 줄 요약

사용자가 "금요일 저녁에 술약속"이라고 말하면 ① LLM이 일정(제목·날짜·카테고리)만 뽑고 ② **서버가 거래 기록으로 금액을 예측**하고 ③ LLM은 서버가 준 값을 자연스럽게 전해 "11/6(금)에 27,300원 쓸 예정으로 등록할까요?"라고 묻고 ④ 사용자가 확인(또는 금액·날짜 수정)하면 기존 예정 지출로 등록하며 ⑤ **예정 지출이 하루 예산·전체 예산 계산에 들어간다.**

## 결정 (사용자가 채팅에서 고름)

1. **예산 반영 방식 = 예약 차감 + 그날 예산 가산.** 예정 금액을 수입일까지 남은 생활비에서 먼저 빼서 다른 날의 하루 예산은 줄고, 약속 당일 하루 예산에는 그 예정 금액을 더한다. 고정지출 "남겨 둘 돈"과 같은 방식이다.
2. **반영 대상 = 예정 지출 전체.** AI 메이트로 만든 것과 달력에서 직접 만든 것이 같은 목록·같은 규칙이다. 따라서 `policies.md` §6 "예산·캐릭터·소비 분석에서 차감하지 않는다" 중 **예산 부분이 바뀐다**(캐릭터 점수·소비 분석은 그대로 반영하지 않음).
3. **기록이 적으면 메이트가 금액을 되묻는다.** 서버가 숫자를 지어내지 않는다.
4. 기술 판단(내가 고름, 이견 있으면 알려 주세요): 새 테이블·마이그레이션 없음(기존 `scheduled_expenses` 재사용), 등록은 새 쓰기 API 없이 기존 `POST /scheduled-expenses`, LLM 호출은 일정이 감지됐을 때만 2번.

## 이전 결정과의 관계

- 2026-10-28 AI 메이트 결정 4번 "거래·고정지출·잔액은 챗봇이 바꾸지 않는다, 배분 변경은 제안만 하고 사용자가 확인하면 앱이 저장": **그대로 지킨다.** 챗봇 서버는 저장하지 않고 제안(`action`)만 돌려주며, 앱이 확인 뒤 기존 API로 저장한다. 제안 종류가 `DAY_PRESET` 하나에서 `SCHEDULE`이 더해진다.
- 같은 결정 3번 "모델에는 서버 계산 예산 요약과 카테고리 합계까지만": **그대로.** 새로 모델에 가는 것은 사용자가 방금 입력한 문장과 서버가 계산한 예측 결과(금액·날짜·카테고리 이름·표본 수)다. 예정 지출 제목은 모델에 보내지 않는다. 개인정보처리방침 개정 전 운영 키를 켜지 않는 결정도 유지.
- 2026-10-30 예정 지출 결정: "예산에 자동 반영 안 함"이 이번에 바뀐다. 실제 거래 자동 생성은 여전히 하지 않는다.

## 금액 예측(서버, `chat` 패키지 안 새 `ScheduleEstimator`)

LLM은 금액을 만들지 않는다. 입력은 모델이 고른 카테고리·시간대·날짜뿐이다.

1. 대상: 본인 **지출** 거래 중 해당 카테고리, 최근 90일(서울 기준 어제까지), `fromFixed`(고정지출 자동 기록) 제외.
2. 같은 날 같은 시간대(아침 06–11, 낮 11–17, 저녁·밤 17–06)의 지출을 **합쳐 한 번의 "자리"로 본다**(1차·2차를 합친 금액이 약속 한 번의 비용).
3. 같은 시간대 자리가 3개 이상이면 그 **중앙값**, 3개 미만이면 카테고리 전체 자리(날짜 단위) 3개 이상일 때 그 중앙값(`basis.scope=CATEGORY`), 그래도 3개 미만이면 **예측 없음**(`amount=null`, 메이트가 금액을 되묻는다).
4. 100원 단위로 내림(예: 27,342 → 27,300). 평균이 아니라 중앙값을 쓰는 이유는 가끔 있는 큰 회식이 예측을 끌어올리지 않게 하려는 것이다.
5. 응답 `basis`: `{samples: 표본 수, scope: SLOT|CATEGORY, days: 90}` — 문구는 "최근 석 달 비슷한 저녁 5번 기준"처럼 말하고 계좌 연결·소비 패턴 분석을 암시하지 않는다.

## 예산 계산 변경(`BudgetCalculator`, `policies.md` §2에 추가할 규칙)

활성 예정 = 날짜가 **오늘 이상 ~ 다음 수입일 전날 이하**인 예정 지출(`plannedByDate`). 수입일 이후 날짜는 다음 주기 일이라 이번 계산에 안 넣고, 지난 날짜는 더 이상 잡아 두지 않는다(그날 쓴 돈은 실제 거래로 이미 반영).

| 값 | 규칙 |
|---|---|
| `reservedPlanned` 남겨 둘 예정 지출 | **내일 ~ 수입일 전날** 예정 금액 합(고정지출과 같은 기준: 오늘 것은 거래로 들어오므로 `remaining`에서 빼지 않는다) |
| `remaining` | 기존 식에서 `− reservedPlanned` |
| 나눌 돈(pool) | max(0, `remaining` + `todaySpent` − **오늘 예정 금액**) — 오늘 예정 금액은 오늘 몫으로 따로 떼어 둔다 |
| 날짜별 하루 예산 | 그 날짜 요일 비중대로 pool을 나눈 몫(기존 `DayWeights.split`) + **그 날짜 예정 금액** |
| `dailyBudget` | 오늘 날짜의 위 값. `todayAvailable` = `dailyBudget` − `todaySpent` |
| `weekAvailable` | 오늘~이번 주 마지막 날(`weekDaysLeft`)까지 **날짜별** 하루 예산 합 − `todaySpent` (요일별 `dayBudgets`가 아니라 날짜별 값을 쓴다) |
| `dayBudgets` | 요일별 **기본 몫**만(예정 가산 제외). 같은 요일이 주기에 여러 번이라 예정을 요일 값에 섞을 수 없기 때문 |
| `dayPlans`(새) | 예정이 있는 날짜의 `[{date, planned, budget}]` — `budget`이 그날 하루 예산(몫 + 예정) |

- 예정 지출이 없으면 모든 값이 지금과 **똑같다**(기존 `policies.md` §2 예시 ①~⑥이 그대로 통과해야 한다).
- 자정에 약속 당일이 오면 `reservedPlanned`에서 빠지고 당일 몫으로 옮겨 간다. 약속 당일 실제 지출을 기록하면 `estimatedBalance`가 줄고 `todaySpent`가 늘어 pool이 변하지 않으므로 이중 차감되지 않는다.
- 예시(11/5 목, 가정): 오늘 pool 기준 몫이 하루 30,000원이고 11/6(금) 27,300원 등록 → 금요일 하루 예산 = 몫 + 27,300, 다른 날 몫은 27,300 ÷ 남은 날 비중만큼 줄어든다. 정확한 숫자 표는 구현 PR에서 `tests/policy/budget.json`에 추가한다.
- 예정이 남은 생활비보다 크면 pool은 0으로 막고(음수 방지) 그날 예산은 예정 금액 그대로다. `remaining`이 음수가 되면 기존처럼 `shortage`로 보인다.
- 예정 지출 수정·삭제는 즉시 다음 `GET /budget/today`에 반영된다. 화면에서 달력의 "예정" 표시와 홈 예산이 항상 같은 값이어야 한다.

## 계약 변경 초안 (`app-api.yaml`, 구현 전 승인 필요)

- `ChatRequest.pending`(선택): 직전에 제안한 일정 `{title, date, categoryId, amount}`. 사용자가 수정 의견을 주면 앱이 함께 보낸다.
- `ChatAction`을 `type: DAY_PRESET | SCHEDULE`로 확장. `SCHEDULE`일 때 `schedule: {title, date, categoryId, category, amount|null, basis|null, preview|null}`. `preview`는 `{dayBudget, dailyBudgetBefore, dailyBudgetAfter}`(서버가 가정 계산한 값, 같은 날짜 기존 예정은 합산).
- `TodayResponse`에 `reservedPlanned`(정수), `dayPlans`(배열) 추가. 기존 필드 의미는 위 표 외에는 그대로(옛 앱은 새 필드를 무시).
- `ChatRequest.accepts`(선택): 앱이 처리할 수 있는 제안 종류(`[SCHEDULE]`). 없으면 서버는 일정 제안을 하지 않는다 — `SCHEDULE`을 모르는 옛 앱이 `action.preset` 없이 확인 버튼을 띄워 저장 오류를 내는 것을 막는다.
- `POST /scheduled-expenses`는 그대로. 삭제·수정 규칙(미래 날짜만 등) 그대로.

## 모델 사용 규칙(`ChatPrompt`)

- 1회차: `propose_schedule(title, date, category, slot, amount?)` 도구. 날짜는 오늘 날짜·요일을 시스템 지시에 주어 모델이 해석하고, "오늘이 아닌 가장 가까운 미래"로 정한다. `amount`는 사용자가 직접 말했을 때만 채운다. 카테고리는 사용자의 지출 카테고리 이름 목록 중에서만 고른다.
- 서버 검증 실패(과거 날짜, 90일 초과, 없는 카테고리)는 메이트가 날짜를 다시 묻는 문장으로 처리하고 저장 제안을 만들지 않는다.
- 2회차: 서버 결과 블록을 주고 "금액·날짜를 바꾸지 말고 묻는 문장 2~3문장"을 쓰게 한다. 금액이 없으면 "얼마 정도 쓸 것 같은지" 묻게 한다. 금액 문자열 검사 실패 시 서버 기본 문장 사용.
- 한 번에 한 일정만 다룬다. 여러 개를 말하면 하나씩 하자고 안내한다.
- 호출 횟수 제한(사용자별 1시간 30번)은 메시지 1건 = 1회로 센다(내부 2회 호출 포함).

## 남은 일 / 위험

- 같은 날짜에 예정이 여럿이면 합산해 가산한다(제한 없음). 예정 건수 상한은 두지 않는다.
- 약속 당일 지나고 남은 예정 기록은 자동 삭제하지 않는다(기존 정책). 달력의 "예정" 표시가 계속 남는 것은 현행 그대로.
- 예측은 "입력한 기록 기준 추정"이며 문구에 "예상"이라고 쓴다.
- 구현·배포 순서: 서버 먼저(필드 추가라 옛 앱 호환), 이후 앱 화면. 운영 Gemini 키가 이미 들어 있다면 개인정보처리방침의 Google 전송 안내(10-28 결정의 선행 조건)가 아직 없는 상태이므로 사람이 먼저 처리한다.
